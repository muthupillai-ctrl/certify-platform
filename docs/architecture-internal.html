Certyfi — Technical Architecture & Scope

Audience: engineers and technical reviewers. Status: reflects the code as of 2026-09-24. Diagrams are Mermaid and render on GitHub and in VS Code's Markdown preview.

Related: technical-approach-summary.md (decisions), test-plan-signing-anchoring.md (verification steps), brochure.md (client-facing summary).

1. Purpose and scope

Certyfi is a multi-tenant platform through which institutions design, issue, manage and publicly verify digital certificates and transcripts. Its defining properties are that issuance needs two different people (maker–checker), and that authenticity does not depend on trusting Certyfi: each certificate is signed under its institution's own key, and the audit ledger is anchored to Bitcoin.

In scope (built)

Area Capability
Tenancy Schema-per-tenant PostgreSQL, tenant resolution, tenant-claim guard, SuperAdmin provisioning
Identity & access JWT auth, 7 roles, role-scoped endpoints and UI routes
Templates Visual canvas designer, imported background images (local uploads), size presets, two legacy fixed layouts
Credentials Draft → approve/reject → active → suspend/reactivate/revoke; custom field schemas; expiry computed live
Audit Hash-chained, append-only ledger_entries (Postgres trigger blocks UPDATE/DELETE) with integrity check
Signing Per-tenant ECDSA P-256 keys, AES-256-GCM at rest, DER signatures, public key endpoint, in-browser verification
Anchoring Periodic ledger checkpoints to Bitcoin via OpenTimestamps; native C# proof parser; downloadable .ots proofs; merkle-root check against a block explorer
Verification Public page + anonymous JSON API + QR codes
Operations SuperAdmin console: tenants, on-demand anchoring

Out of scope / not built

Badge rules engine, standalone revocation registry, DID/wallet support, selective disclosure, legacy-data migration, partner issuance API (a Developer role exists but is not wired), refresh tokens, rate limiting, cloud object storage for uploads, a real cloud KMS provider, signing-key rotation, RFC 8785 canonicalization, MFA (fields exist, flow does not).

Dependency rule: Domain has no framework references; Infrastructure depends on Domain; Api depends on both. Signing and anchoring sit behind interfaces (ITenantSigningKeyProvider, ILedgerCheckpointService) so a cloud KMS or an extracted service can replace them without changing callers.

4. Multi-tenancy and request pipeline

One physical Postgres schema per tenant (tenant_<slug>), plus a platform schema for the tenant registry, platform admins and signing keys.

flowchart LR
    R[HTTP request] --> H{Path exempt?<br/>/api/v1/platform<br/>/api/v1/verify /health /swagger}
    H -- yes --> AUTHN
    H -- no --> TR[TenantResolutionMiddleware<br/>X-Tenant-Slug or subdomain<br/>reject 400/404 if unresolved]
    TR --> AUTHN[JWT authentication]
    AUTHN --> TG[TenantClaimGuardMiddleware<br/>token tenant_id must equal resolved tenant]
    TG --> AZ[Authorization<br/>role policies]
    AZ --> C[Controller]
    C --> DB[(TenantDbContext<br/>schema from ITenantContext)]

Key mechanisms

  • TenantModelCacheKeyFactory caches one compiled EF model per schema.
  • TenantDbContextFactory builds a TenantDbContext for a named schema outside any request (provisioning, background anchoring, the public verify endpoint).
  • Tenant-schema migrations are compiled against a placeholder schema (unresolved) and applied per tenant by generating an idempotent SQL script and substituting the real schema name. They auto-apply in Development. Platform-schema migrations do not; run dotnet ef database update --context PlatformDbContext.
  • A platform-admin token carries no tenant_id; a tenant token carrying a SuperAdmin role is rejected on platform endpoints. SystemRole.TenantAssignable excludes SuperAdmin from tenant seeding and user creation.

Placement: Tenant, PlatformAdmin, TenantSigningKey are in the platform schema (secret management is a platform concern, mirroring a shared KMS account). Everything else is in each tenant's schema.

Design principles

  • Snapshot, not live reference. Achievements copy template fields; credentials copy the field schema. Editing a template never changes an issued certificate's appearance.
  • Expiry is computed at read time, never stored as a status.
  • LedgerEntry uses SequenceNumber as the primary key (explicit HasKey), with Id as an opaque external identifier.

6. Credential lifecycle

stateDiagram-v2
    [*] --> PendingApproval: Create (Registrar / Admin / Learner)
    PendingApproval --> Active: Approve (different user)
    PendingApproval --> Rejected: Reject (different user, reason)
    Active --> Suspended: Suspend (reason)
    Suspended --> Active: Reactivate
    Active --> Revoked: Revoke (reason)
    Suspended --> Revoked: Revoke (reason)
    Rejected --> [*]
    Revoked --> [*]

Expired is a display status derived from ExpiresOn at verification time. Self-approval is blocked by the system, including for Institution Admins. Every transition appends a ledger entry inside the same database transaction as the credential change, so both commit or neither does.

7. Trust layer

Three independent layers, each closing a different attack:

Layer Defends against Mechanism
Record-based verification Edited PDF/image Verification resolves credential ID to the database record
Hash-chained ledger Silent edits to history EntryHash = SHA-256(previous hash + event data); append-only trigger; GET /ledger/integrity re-walks the chain
Signature Forged or altered credential ECDSA P-256 over the canonical hash, tenant key
Bitcoin anchor Whole-database rewrite (including by the operator) OpenTimestamps checkpoints of the ledger tip

7.1 Issuance and signing

sequenceDiagram
    actor Maker as Registrar (maker)
    actor Checker as Approver (checker)
    participant API as CredentialsController
    participant KMS as ITenantSigningKeyProvider
    participant PDB as Platform DB
    participant TDB as Tenant DB

    Maker->>API: POST /credentials/from-template
    API->>TDB: insert Credential (PendingApproval) + ledger "Requested" (one transaction)
    Checker->>API: POST /credentials/{id}/approve
    API->>API: reject if checker == maker
    API->>API: CanonicalHash = SHA-256(fixed-shape JSON)
    API->>KMS: GetOrCreateActiveKey(tenant)
    KMS->>PDB: read or lazily create key (encrypted private key)
    API->>KMS: Sign(tenant, keyId, CanonicalHash)
    KMS->>KMS: decrypt private key (AES-256-GCM), ECDSA sign, DER encode
    KMS-->>API: signature
    API->>TDB: set Active, Signature, KeyId + ledger "Approved" (one transaction)

Signing details

  • Algorithm ES256 (ECDSA P-256, SHA-256). Signatures use RFC 3279 DER (DSASignatureFormat.Rfc3279DerSequence). .NET's default IEEE P1363 format is not interoperable with OpenSSL, Node, Java or Python.
  • The browser's Web Crypto API needs raw P1363, so the frontend converts DER to raw before verifying.
  • Master key: Kms:LocalMasterKey (base64, 32 bytes) from user-secrets or environment, validated at startup. Never in appsettings.json.

7.2 Public verification

sequenceDiagram
    actor V as Verifier (browser)
    participant API as VerificationController (anonymous)
    V->>API: GET /verify/{slug}/{id}
    API-->>V: record, canonicalHash, signature, keyId, algorithm, anchorStatus
    V->>API: GET /verify/{slug}/signing-keys/{keyId}
    API-->>V: public key PEM
    V->>V: Web Crypto ECDSA verify locally
    opt Independent check
        V->>V: openssl dgst -sha256 -verify pub.pem -signature sig.der hash.txt
    end

Verify endpoints are exempt from tenant resolution: the tenant comes from the URL path. Pending and rejected credentials return 404, so the endpoint is not a workflow-state oracle. The response deliberately omits recipient email and all reason fields.

7.3 Ledger anchoring

sequenceDiagram
    participant BG as LedgerAnchorBackgroundService
    participant CS as LedgerCheckpointService
    participant TDB as Tenant DB
    participant CAL as Calendar servers (Alice, Bob, Finney, Catallaxy)
    participant EXP as Blockstream Esplora

    loop hourly, per active tenant
        BG->>CS: RunCheckpointStep
        CS->>TDB: latest LedgerEntry vs last checkpoint
        alt new activity
            CS->>CS: digest = SHA-256(tip EntryHash)
            CS->>CAL: POST /digest (raw 32 bytes)
            CAL-->>CS: serialized Timestamp (pending attestation)
            CS->>CS: merge responses, wrap as .ots
            CS->>TDB: insert LedgerCheckpoint (Pending, OtsProof)
        else no new activity
            CS-->>BG: skip (idempotent)
        end
    end
    loop every 3 hours
        BG->>CS: RunUpgradeStep
        CS->>CAL: GET /timestamp/{digest hex}
        CAL-->>CS: upgraded Timestamp (or 404)
        CS->>CS: merge, then search tree for Bitcoin attestation
        opt Bitcoin attestation found
            CS->>EXP: block at height, read merkle_root
            CS->>CS: byte-reverse and compare to attestation leaf message
            CS->>TDB: Status=Confirmed, height, MerkleRootVerified
        end
    end

A credential's anchor status comes from the earliest checkpoint whose UpToSequenceNumber covers that credential's latest ledger entry: NotYetCheckpointed, Pending or Confirmed.

7.4 OpenTimestamps format (implemented natively in C#)

Ported from the python-opentimestamps reference source, then cross-checked with the official ots CLI.

flowchart TB
    F[".ots DetachedTimestampFile"] --> M["31-byte magic header"]
    F --> VER["version byte = 1"]
    F --> HOP["file hash op tag (0x08 = SHA-256)"]
    F --> DIG["32-byte digest"]
    F --> TS["Timestamp tree"]
    TS --> T1["0xff = more siblings follow"]
    TS --> T2["0x00 = attestation follows"]
    TS --> T3["op tag = edge to child Timestamp"]
    T2 --> A1["Pending: 83dfe30d2ef90c8e + calendar URI"]
    T2 --> A2["Bitcoin: 0588960d73d71901 + varuint height"]
    T3 --> O["Append f0 / Prepend f1 / SHA-256 08<br/>(also parsed: Reverse f2, Hexlify f3, SHA-1 02, RIPEMD-160 03)"]

Primitives: unsigned LEB128 varuints; varbytes = varuint length + bytes. Unknown attestation tags are preserved as opaque data. Byte order note: an attestation's message is the merkle root in internal order; block explorers display it reversed, so the comparison reverses first.

8. Security model

Concern Control
Cross-tenant access Schema isolation; resolved tenant checked against JWT claim on every request
Privilege escalation Tenant role list excludes SuperAdmin; platform tokens carry no tenant claim
Self-approval Enforced in Approve/Reject, no role exemption
History tampering Hash chain + append-only DB trigger + Bitcoin anchoring
Credential forgery Per-tenant ECDSA signatures, public keys served anonymously
Key compromise blast radius One key per tenant; a tenant key cannot sign for another
Private key at rest AES-256-GCM with master key outside the database
Secrets in source Jwt:SigningKey, Kms:LocalMasterKey, DB string via user-secrets or env; validated at startup
PII exposure on verify DTO excludes email and reason fields
Custom-field injection Field values validated against the credential's own schema snapshot

Known weaknesses: no rate limiting on login or verify, no refresh tokens, no MFA flow, uploads on local disk, signed payload not RFC 8785 canonical.

10. Frontend architecture

  • Angular standalone components with signals; Tailwind for styling; lazy-loaded routes.
  • Guards: authGuard and roleGuard([...]). authInterceptor attaches the bearer token and X-Tenant-Slug.
  • Route areas: /login, /admin/* (staff), /admin/templates/new|:id/edit (full-screen canvas editor), /platform/* (SuperAdmin), /verify/:slug/:id (public).
  • CertificatePreviewComponent renders both legacy layouts and canvas layouts, scaling large canvases to fit via ResizeObserver and CSS transform.
  • SignaturePanelComponent verifies signatures with Web Crypto. AnchorPanelComponent shows Bitcoin status and the proof download. Both appear on the public page (hidden in print) and the admin Verification tab.

11. Deployment, configuration and operations

Local: docker compose up -d (Postgres 16 on host port 5433), backend on http://localhost:5080, Angular dev server on http://localhost:4200.

Required configuration (user-secrets or environment)

Key Purpose
ConnectionStrings:Default PostgreSQL
Jwt:SigningKey JWT HMAC key
Kms:LocalMasterKey Base64 32-byte key for private-key encryption
SuperAdminSeed:Email / Password Bootstraps the first platform admin (Development only)

Operational notes

  • Development startup seeds the SuperAdmin and migrates every tenant schema. Elsewhere, tenant migration is the SuperAdmin migrate-schemas action.
  • Platform migrations are always manual.
  • The background anchoring service starts about 30 s after boot, checkpoints hourly and checks confirmations every 3 hours (constants in LedgerAnchorBackgroundService). It needs outbound HTTPS to the four calendar servers and blockstream.info.
  • Running multiple API instances would run the anchoring loop on each. Checkpoints are idempotent per sequence number (unique index), but a shared lock would avoid duplicate calendar submissions.

12. Testing

dotnet test runs 77 integration tests against a throwaway Postgres container per test class (Testcontainers): tenancy isolation, privilege escalation, maker–checker, templates, custom fields, ledger integrity, signing (including a tamper check), OpenTimestamps binary round trips against a real captured calendar response, and real-network anchoring tests.

Independent verification is deliberate practice: signatures were checked with OpenSSL and Node, and .ots proofs with the official ots CLI, because same-language tests once passed while a signature format was non-interoperable. See test-plan-signing-anchoring.md.

13. Roadmap and open decisions

  1. Cloud KMS provider (AWS KMS / Azure Key Vault) behind ITenantSigningKeyProvider.
  2. Signing-key rotation with retired keys retained for old signatures.
  3. RFC 8785 canonicalization of the signed payload.
  4. Partner API: API keys or OAuth client credentials, scopes, rate limits, docs.
  5. Object storage for uploads; refresh tokens; rate limiting; MFA.
  6. Checkpoint listing in the SuperAdmin UI; leader election for the anchoring loop.
  7. Extract signing and anchoring into a standalone Trust-Ledger service if sold per vertical.
  8. Badge rules, revocation registry, DID/wallets, selective disclosure, migration tooling.
